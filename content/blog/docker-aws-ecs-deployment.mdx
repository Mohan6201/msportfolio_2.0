When the Txenia AI/ML WMS platform needed to run three separate services — a prediction engine, a data-sync worker, and a reporting API — on the same cluster without them interfering with each other, containers were the obvious answer. Here's exactly how we containerized each service and deployed them to Amazon ECS.

## The Services

| Service | Language | Memory | vCPU |
|---------|----------|--------|------|
| Prediction | Python / FastAPI | 2 GB | 1 |
| Data Sync | Python worker | 512 MB | 0.25 |
| Reporting | Django REST | 1 GB | 0.5 |

Each service has its own ECR repository and ECS task definition. They communicate over an internal ALB — nothing is exposed publicly except the reporting API.

## Writing Lean Dockerfiles

The biggest win was switching from `python:3.11` (1.1 GB) to `python:3.11-slim` (150 MB) for all three services. The prediction service dockerfile:

```dockerfile
FROM python:3.11-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

The multi-stage build keeps the final image small — dependencies are installed in the builder stage and only the `.local` packages are copied across. No build tools end up in the production image.

## ECS Task Definition

```json
{
  "family": "txenia-prediction",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "1024",
  "memory": "2048",
  "containerDefinitions": [
    {
      "name": "prediction",
      "image": "123456789.dkr.ecr.ap-south-1.amazonaws.com/txenia-prediction:latest",
      "portMappings": [{ "containerPort": 8000 }],
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group": "/ecs/txenia-prediction",
          "awslogs-region": "ap-south-1",
          "awslogs-stream-prefix": "ecs"
        }
      },
      "healthCheck": {
        "command": ["CMD-SHELL", "curl -f http://localhost:8000/health || exit 1"],
        "interval": 30,
        "timeout": 5,
        "retries": 3,
        "startPeriod": 60
      }
    }
  ]
}
```

The `startPeriod: 60` gives the ML model time to load into memory before ECS starts counting health check failures — without it, ECS would kill the container before it was ready.

## Auto-Scaling Configuration

ECS Application Auto Scaling tracks two metrics simultaneously:

```python
# Two scaling policies — ECS scales on whichever threshold is hit first
scaling_policies = [
    {
        "PolicyName": "cpu-scaling",
        "TargetTrackingScalingPolicyConfiguration": {
            "TargetValue": 70.0,
            "PredefinedMetricSpecification": {
                "PredefinedMetricType": "ECSServiceAverageCPUUtilization"
            },
            "ScaleOutCooldown": 60,
            "ScaleInCooldown": 300
        }
    },
    {
        "PolicyName": "memory-scaling",
        "TargetTrackingScalingPolicyConfiguration": {
            "TargetValue": 75.0,
            "PredefinedMetricSpecification": {
                "PredefinedMetricType": "ECSServiceAverageMemoryUtilization"
            }
        }
    }
]
```

Scale-in cooldown is intentionally longer (300 s vs 60 s) — we'd rather keep a warm container running than terminate it and pay the cold-start cost again.

## Zero-Downtime Deployments with Blue/Green

CodeDeploy handles traffic shifting. The `appspec.yaml` in our repo:

```yaml
version: 0.0
Resources:
  - TargetService:
      Type: AWS::ECS::Service
      Properties:
        TaskDefinition: <TASK_DEFINITION>
        LoadBalancerInfo:
          ContainerName: prediction
          ContainerPort: 8000
Hooks:
  - BeforeAllowTraffic: "arn:aws:lambda:ap-south-1:123:function:smoke-test"
  - AfterAllowTraffic: "arn:aws:lambda:ap-south-1:123:function:notify-slack"
```

The `BeforeAllowTraffic` Lambda runs a quick smoke test against the green environment. If it returns a non-200, CodeDeploy rolls back automatically — no human involvement required.

## CloudWatch Dashboards

Every service gets a dashboard with four widgets:

1. **Request count** — ALB RequestCount per service
2. **P99 latency** — ALB TargetResponseTime at p99
3. **Error rate** — 5xx responses / total requests
4. **Container health** — ECS RunningTaskCount vs desired

Setting a CloudWatch alarm on the prediction service's P99 latency was what caught a memory leak before it hit production. The task was slowly accumulating un-GC'd tensors; the rising latency alarm fired hours before the container would have OOM-crashed.

## Takeaways

- **Fargate over EC2** for services with variable load — no node management, and Spot Fargate cut compute costs by 40%.
- **One ECR repo per service** — makes IAM policies straightforward and avoids accidental cross-service image pulls.
- **Health check `startPeriod`** is not optional for ML workloads — model load time is real and ECS will kill your container without it.
- **Always add a smoke test hook** to blue/green deployments — it's the last line of defence before traffic shifts.
